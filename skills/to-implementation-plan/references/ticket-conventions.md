# Ticket conventions (reference)

## Where files go

An implementation plan (kebab-case `<scope>`, named for its intent) groups everything under
`specs/<scope>/`:

- `specs/<scope>/SPEC.md`: the design source of truth.
- `specs/<scope>/tickets/<name>-ticket.md`: one ticket per session-sized deliverable.
- `specs/<scope>/MAP.md` and `frontier.sh`: the index and the frontier query, born together.
  `.dashboard/` beside them is gitignored and regenerated by the skill's `assets/dashboard.js`.
- `specs/<scope>/assets/<name>.md`: long context linked from SPEC.md or a ticket.
- `specs/<scope>/spikes/<name>.md`: exploratory write-ups.
- Companion design docs (`CONTEXT.md`, `DATA_MODEL.md`) sit next to SPEC.md.

ADRs live under `docs/adrs/`, outside the specs tree; they outlive any single plan. Reference
material cited but not authored (vendor API docs, source PDFs) goes under `docs/refs/<context>/`.
`<root>` is the repo root, or the package dir in a monorepo: `packages/<pkg>/specs/<scope>/` and
`packages/<pkg>/docs/adrs/`.

A ticket links back to its spec and companions (`../SPEC.md`, `../DATA_MODEL.md`) and to
ADRs/refs; it doesn't duplicate their rationale.

## Naming

- Scope: short, descriptive, hyphenated when more than one word, derived from the intent unless the
  user names it.
- Tickets: kebab-case plus the `-ticket.md` suffix, no ordinal in the filename (order encoded in
  names is what made `phase-1-m2.5-…` painful to insert or reorder). Order lives in `blockedBy`
  edges.
- Refer to sibling tickets by name/path, never by number.

## Status

- yaml frontmatter on top of each ticket: `status: ready | in-progress | blocked | parked | done`,
  plus `blockedBy:` (sibling ticket filenames and/or quoted one-line human prerequisites, as a
  block list) when blocked or parked.
- Task checkboxes (`- [ ]` / `- [x]`) carry the live work state. Tick immediately, never batch.
- Nothing else stores status: no status tables, and MAP.md stays status-free. The gitignored
  `.dashboard/` page is a view regenerated from the tickets by the skill's `assets/dashboard.js`,
  not a store.

## Scaffolding

Dependency-free Node helpers. Run them from the target repo root (`--repo-root` defaults to the
current directory), by their path inside this skill:

- `node <skill-dir>/scripts/new-ticket.js --scope <scope> --title "Deposit projection"` creates
  `specs/<scope>/tickets/<slug>-ticket.md` from the template. `--update-index` also lists it in
  MAP.md (created from `assets/templates/map-template.md` on first use, together with
  `frontier.sh`).
- `node <skill-dir>/scripts/bootstrap-spec.js --scope <scope>` scaffolds
  `specs/<scope>/{tickets,spikes,assets}/`. It creates neither SPEC.md (a designed artifact,
  authored through the spec gate) nor MAP.md.

If you can't run scripts, copy the templates under `assets/templates/` and fill them in.

## MAP.md (the map)

The whole implementation plan at low resolution, loaded once per session; zoom into a ticket on
demand. It is an index, not a store: one line per ticket, enough to judge relevance, then the link
for detail. It never restates ticket content and never mirrors live status (that lives in each
ticket's yaml). Its "How this works" section is the working agreement: claim by
`status: in-progress` before any work, close by `status: done` plus the final Update plus a
one-line outcome gist on the ticket's entry, max one ticket implemented per session.

`frontier.sh` sits next to MAP.md (both born on the first `new-ticket.js --update-index`) and
prints the takeable tickets: `status: ready`, or `blocked` whose listed `*-ticket.md` blockers are
all `done`; a prose prerequisite blocks until the author removes it. Its output is unordered; the
`Next up:` cursor decides what's next.

The map may carry the one **`Next up:`** cursor, a best-effort forward pointer to the next ticket,
the only ordering fact that isn't derivable (for "last worked", read `git log` or the newest
`**Update (…)**`). Verify the target ticket's yaml status before trusting it; update it when you
start or finish a ticket. One home only: MAP.md, or the top of SPEC.md if no MAP.md exists.

## Legacy layout (`plans/`)

Older scopes live under `plans/<scope>/` as `plan.md`, `prds/<name>-prd.md`, `README.md` and a
`frontier.sh` that scans `prds/`. When such a scope is picked up, move it to the current layout
before touching its content: `plans/<scope>/` to `specs/<scope>/`, `plan.md` to `SPEC.md`,
`prds/` to `tickets/` with the `-ticket.md` suffix, `README.md` to `MAP.md`, and `frontier.sh`
replaced by a fresh copy of `assets/frontier.sh`. Fix `blockedBy` paths and MAP links to match, and
tell the user what moved so they can commit it.
